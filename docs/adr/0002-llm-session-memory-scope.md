# 같은 Session 안의 직전 N 턴 **메타만** LLM 에 주입한다 — 데이터 행은 넣지 않는다

매 `/chat` 호출 시 서버가 같은 Session 의 직전 **5턴**을 조회해 `{ 사용자 질의, 생성된 DB 쿼리, 결과 메타(columns·rowCount), assistant 응답 }` 을 프롬프트에 prepend 한다. **Attachment 의 데이터 행(`data`) 은 절대 LLM 에 보내지 않는다.** 이 아키텍처(LLM 이 쿼리를 생성 → 서버가 실행) 에선 후속 질의 대부분이 쿼리 수정이므로 데이터 값은 불필요하다. 민감 컬럼 필터 (#227) 와 궁합을 맞춰, 데이터 값이 LLM 공급자 서버로 송신될 가능성 자체를 차단한다.

## Considered Options

- **메모리 완전 없음** (원안): 매 질의 독립. 가장 단순하지만 "방금 결과에서 X 컬럼만" 류 후속 질의가 성립하지 않아 매번 사용자가 full context 를 재입력해야 함. 추가 공수를 아끼기 위해 UX 를 희생.
- **직전 N 턴 메타만** (채택): 턴당 ≈ 100-300 토큰. 후속 쿼리 수정 대부분 커버. 공수 1-2시간 수준 (`history-db.ts.getRecentMessages` + `/chat` 핸들러 10-15줄).
- **전체 history + 데이터 행까지 주입** (거절): 10만 행 테이블이면 즉시 컨텍스트 초과. 토큰 비용·보안 리스크(민감 데이터 송신)·요약 전략 복잡도 모두 폭증. "방금 결과의 평균 계산해줘" 류 데이터 접근 질의를 지원하기 위한 대가가 너무 큼. Phase 2 이상.

## Consequences

- 사용자가 데이터 값을 참조하는 질의 ("그 중 timon 사용자만") 는 LLM 이 응답하지 못함 — "값을 쿼리 조건으로 명시해 주세요" 로 되돌아간다. UX 상 수용.
- `messages` 테이블에 `generated_query TEXT` 컬럼이 추가된다 (LLM 재주입 소스).
- CLI 공급자 (claude · codex · gemini) 는 stateless 호출 유지. 공급자별 세션 재개 기능은 쓰지 않음 — 호환성 유지.
- 민감 컬럼 필터 (#227) 는 **파일 저장 시점** 뿐 아니라 **LLM 응답 시점** 에서도 안전 — 애초에 데이터가 안 넘어가므로.
